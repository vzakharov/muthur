# Review board по частям изменения

Запрос (Вова, 15.11.2026): переделать `/review-board` по образцу страницы, где
строки — части изменения, а не файлы; обобщить на любой PR и на часть PR (с
последнего ревью, с последнего просмотренного коммита, по диапазону); сохранить
комментарии к строкам, которые приходят Claude, и ссылку в закреплённом
комментарии PR.

## Чем нынешняя доска тяжела и неудобна

Замер на PR #269 (38 файлов, +1611/−204): страница весит **1,19 МБ**.

- **877 КБ — вложенные данные**: полный текст каждой версии каждого изменённого
  файла на каждом коммите ветки. Их кладёт сборщик (`scripts/collect.ts`,
  `readRevisions` → `readBlobs`), чтобы страница сама считала дифф между любыми
  двумя коммитами и «сдвигала» файл после комментария. Вес растёт как файлы ×
  коммиты × размер файла, а не как дифф.
- **304 КБ — скрипт**: движок доски (пан и зум, укладка карточек, свои пины
  комментариев), highlight.js, markdown-it, zod.
- **Единица — файл, а не смысл.** 38 карточек на двумерном поле, которое надо
  двигать и масштабировать; порядка чтения нет. Смысл живёт только в коротком
  списке фокуса (`review-focus.json`) и в папках. Что поменяли и почему, каким
  коммитом — на доске нет вовсе.
- **За это платим ~8 тыс. строк TypeScript** в FSD-слоях (камера, укладка,
  папки, выделение области, история «просмотрено», затенение по возрасту,
  поповеры, фильтр). Свои пины комментариев нужны только потому, что поле
  двигается CSS-трансформацией.

Образец весит 750 КБ, но это 450 файлов почти целиком в разметке; скрипта в нём
766 байт. Лёгкость там — от того, что страница статическая, а не от размера
данных.

## Что строим

Одна статическая страница-колонка, как в образце. Сборщик читает git и файл
частей, который ведёт агент, проверяет одно против другого и падает на
противоречии; страница несёт только дифф выбранного диапазона, уже отрисованный
в HTML, и пару килобайт скрипта.

### Страница

- **Строка-сводка сверху**: дата сборки, PR и ветка, диапазон «от `abc1234`
  (ревью от 14.11) до `def5678`», число частей и файлов. Все ссылки — на GitHub
  с закреплённым полным SHA.
- **Части** — `<details>`, по умолчанию свёрнуты. В заголовке: название, статус,
  одно предложение, счётчики `+/−`. Часть с пометкой фокуса подсвечена и несёт
  своё «почему» — это то, во что превращается нынешний `review-focus.json`.
- **Внутри части**: список правок «что поменяли — почему — коммиты» (ссылки на
  коммиты), затем файлы. Файл — тоже `<details>`, свёрнут; раскрывается в
  унифицированный дифф с тремя строками контекста, со ссылкой на файл на GitHub
  на голове диапазона.
- **Шум снят до показа**: переименование без правок показывается строкой
  «перенесён», без диффа; файлы из `ignore` (лок-файлы, сгенерированное) — без
  диффа, с причиной; подстановки из `normalize` применяются к обеим сторонам до
  сравнения и перечислены в шапке, как переименования пространств имён в
  образце.
- **Дифф одного файла длиннее 2000 строк** не встраивается: строка «слишком
  большой, открыть на GitHub». Это потолок веса, а не вкус.
- **Без подсветки синтаксиса и без рендера Markdown** — это две трети нынешнего
  скрипта, в образце их нет.
- Переключатель темы, токены цвета на `:root`, тёмная тема — как в образце.

### Данные, которые пишет агент

`docs/remove-before-merging/review-parts.json`, коммитится, заменяет
`review-focus.json`:

```json
{
  "parts": [
    {
      "id": "anchor-grammar",
      "title": "Грамматика якорей комментариев",
      "summary": "Одно предложение о том, что это.",
      "status": "changed",
      "focus": "Почему стоит читать внимательно (необязательно).",
      "files": [".claude/artifacts/src/review-board/**/anchor*.ts"],
      "changes": [
        { "text": "Что поменяли.", "why": "Почему.", "commits": ["1a2b3c4"] }
      ]
    }
  ],
  "normalize": [{ "from": "OldName", "to": "NewName", "why": "…" }],
  "ignore": [{ "glob": "**/pnpm-lock.yaml", "why": "лок-файл" }]
}
```

Схема — zod, тип выводится из неё. Тексты — на языке сессии.

### Проверки сборщика (падает и перечисляет всё найденное разом)

- файл из диффа PR не попал ни в одну часть (файл берёт первая часть, чей шаблон
  его поймал);
- шаблон части не поймал ни одного файла;
- коммит правки не найден или не лежит между базой PR и его головой;
- статус противоречит файлам: `new` — а среди файлов есть не добавленные;
  `removed` — есть не удалённые; `moved` — есть не переименованные; `changed` —
  а все файлы добавлены;
- пустые `title`, `summary`, `why`; повторный `id`;
- шаблон `normalize` или `ignore` ничего не поменял / не поймал.

Части описывают **весь PR**, а не диапазон: так файл частей не переписывается
при каждом новом ревью. На частичном диапазоне страница показывает только части
с файлами в диапазоне и только правки с коммитами в нём; остальные части
сворачиваются в одну строку «без изменений с `abc1234`: …».

### Диапазоны

`node .claude/artifacts/src/review-board/scripts/build.ts [--from <spec>] [--to <rev>]`,
по умолчанию весь PR (merge-base..HEAD).

- `--from review` — `commit_id` последнего ревью оператора на PR
  (`gh api repos/…/pulls/<n>/reviews`); нет ревью — сборка падает с этим
  текстом.
- `--from seen` — коммит, который Вова отметил кнопкой «Просмотрено до сюда» на
  странице (см. вопрос 2). Сборщик читает его из файла, который агент перед
  сборкой заполняет через `ArtifactData get` — сборщик сам в базу артефакта не
  ходит.
- `--from <sha>` и `--to <sha>` — явный диапазон; оба должны лежать на ветке PR.

Одна страница на PR, по ссылке из закреплённого комментария: сборка с диапазоном
переопубликовывает её же, а шапка говорит, какой диапазон на ней.

### Комментарии к строкам

Остаётся всё, что работает: комментарий, отправленный Claude со страницы, будит
сессию и разбирается как ревью (`/go` § «Planless entry», ответ с SHA, треды не
закрываем); ссылка — в закреплённом комментарии через
`scripts/pr-comment.sh review-board`.

Меняется способ якорения. Страница больше не двигается, поэтому свои пины
(`customAnchors`) не нужны: каждая строка диффа получает `id` с нынешней
грамматикой якоря `<path>@<from7>..<to7>:R<n>` / `:L<n>` и
`data-comment-target`, и якорит оболочка артефакта. Шаг 3 навыка (расшифровка
якоря) остаётся почти как есть. **Первым делом в `/go` — проверка в `tmp/`**:
опубликовать маленькую страницу и убедиться, что якорь треда приходит Claude с
читаемым `id` и что пин встаёт внутри раскрытого `<details>`. Если нет —
откатываемся на `customAnchors` с маленьким скриптом поверх той же разметки
(вопрос 3).

### Что уходит

- Двумерное поле, камера, укладка, папки, выделение области, панель.
- Вложенные версии файлов и «сдвиги» (`shifts` в базе артефакта): их работу —
  показать файл с того места, где Вова остановился, — делает `--from seen` /
  `--from review` для всей страницы.
- История «просмотрено» по файлам, затенение по возрасту, поповеры, фильтр по
  пути.
- `review-focus.json` — его смысл переезжает в `focus` части.

Мешает ли что-то из сохраняемого: нет. Ничто из нынешнего не нужно сохранять
ради комментариев, кроме грамматики якоря, а она дешёвая.

## DRY notes

- **Переиспользуется**: `scripts/pr-comment.sh` (закреплённый комментарий),
  грамматика якоря из `pages/board/comments/lib/anchor.ts` (переезжает вниз, в
  `shared` нового приложения, вместе с тестами), разбор git-статусов и
  `merge-base` из `scripts/collect.ts` (`readChanges`, `readCommits`,
  `resolveBaseRef`) — они остаются, `readRevisions`/`readBlobs` уходят.
- **Дифф** берём у `git diff -M` по диапазону, а не считаем свой: нынешний
  `shared/lib/diff.ts` был нужен, чтобы страница считала дифф в браузере между
  любыми коммитами; сборщику это не нужно. `normalize` при этом требует
  сравнения уже подставленных текстов — для таких файлов сборщик кормит
  `git diff --no-index` двумя временными файлами, а не заводит свой алгоритм.
- **Схема файла частей** — одна, zod; тип и проверки выводятся из неё. Проверки,
  которые зависят от git (файлы, коммиты, статусы), — отдельный модуль сборщика,
  потому что схема их выразить не может.
- **Сборщик образца** (Python) не переносится: в muthur уже есть Node-цепочка
  для артефактов, вторая цепочка ради одной страницы — чистый минус.

## Вопросы к Вове

   кнопка «Просмотрено до сюда» в шапке страницы пишет SHA головы в базу
   артефакта (с тем, кто нажал); агент читает его перед сборкой. b) голова той
   версии страницы, к которой ты последний раз оставил комментарий — без кнопки,
